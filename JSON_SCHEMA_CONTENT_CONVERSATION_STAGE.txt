하데스 보카 - 실전회화 Stage 콘텐츠 JSON 가이드
================================================

문서 목적
- 실전회화 Stage JSON과 에셋을 추가할 때 따를 표준 구조를 정리한다.
- 앱은 JSON 본문을 사용자 저장 데이터에 복사하지 않고, 완료/오답/저장 표현은 참조 ID만 저장한다.
- 현재 기준은 Stage 1 Day 1~7의 통일된 구조다.


1. 폴더 구조
------------

Stage별 회화 콘텐츠는 Stage 폴더 하나에 묶는다.

  public/content/conversations/
    stage-{stageId}/
      index.json
      day-{DD}.json
      assets/
        stage-{stageId}-day-{DD}-cutscene.jpg
        stage-{stageId}-day-{DD}-scene-01.jpg
        stage-{stageId}-day-{DD}-scene-02.jpg
        stage-{stageId}-day-{DD}-scene-03.jpg

공유 fallback 이미지만 아래 폴더에 둔다.

  public/content/conversations/assets/
    placeholder-day1-cutscene.svg
    placeholder-day2-cutscene.svg
    placeholder-day3-cutscene.svg


2. index.json
-------------

index.json은 Stage 메타 정보와 Day 파일 목록만 가진다.
Day 본문 데이터는 index.json에 넣지 않는다.

필드
  schemaVersion      | string   | 예: "1"
  stageId            | number   | 회화 스테이지 ID
  stageTitleKo       | string   | 선택
  stageDescriptionKo | string   | 선택
  dayFiles           | string[] | 이 Stage를 구성하는 Day 파일명 목록

원칙
- dayFiles에는 실제 파일명을 직접 쓴다.
- dayFiles 순서가 앱에서 조립되는 days 순서가 된다.
- 파일명은 day-01.json처럼 두 자리 형식을 권장한다.

예시
{
  "schemaVersion": "1",
  "stageId": 1,
  "stageTitleKo": "Stage 1 · 실전 회화",
  "stageDescriptionKo": "짧은 장면들로 구성된 비주얼노벨형 회화 흐름입니다.",
  "dayFiles": [
    "day-01.json",
    "day-02.json",
    "day-03.json",
    "day-04.json",
    "day-05.json",
    "day-06.json",
    "day-07.json"
  ]
}


3. 앱 로딩 계약
---------------

- getConversationStage(stageId): Promise<ConversationStage> 계약을 유지한다.
- 로더는 stage-{stageId}/index.json을 읽고, dayFiles에 적힌 day-xx.json을 추가로 읽는다.
- 앱 내부 최종 형태는 ConversationStage이며, 화면 컴포넌트는 stage.days를 사용한다.
- public/content/stage-metadata.json은 현재 conversation content path를 직접 들고 있지 않다.

ConversationStage
  schemaVersion      | string
  stageId            | number
  stageTitleKo       | string | 선택
  stageDescriptionKo | string | 선택
  days               | ConversationDay[]


4. Day 표준 구조
----------------

각 day-xx.json은 ConversationDay 객체 하나만 담는다.

필드
  dayId              | number | 회화 일차. UserProgress 참조키
  difficulty         | string | 선택. "low" | "medium" | "high"
  titleKo            | string
  descriptionKo      | string | 선택
  sceneDescriptionKo | string | 장면 요약. 선택
  cutsceneImagePath  | string | 대표 컷씬/목록 썸네일 이미지
  sceneImages        | object | 내부 장면 이미지. intro/dialogue/review 권장
  narrations         | array  | ConversationNarration[]
  dialogue           | array  | ConversationDialogueLine[]. 키 이름은 dialogue
  keyExpressions     | array  | ConversationKeyExpression[]
  quiz               | array  | ConversationQuiz[]. 키 이름은 quiz

Stage 1 현재 표준 수량
- 대표 컷씬 1장
- sceneImages 3장: intro, dialogue, review
- narrations 2개
- dialogue 6줄
- responseQuiz 2개
- keyExpressions 3개
- quiz 4개

difficulty 원칙
- Day 단위 난이도 메타데이터다.
- 허용값은 "low", "medium", "high"만 쓴다.
- 앱 표시 라벨은 코드에서 매핑한다.
  - low: 하 · 초급
  - medium: 중 · 기본
  - high: 상 · 심화
- 난이도는 안내 정보이며, 잠금/해금 조건으로 사용하지 않는다.
- 기존 콘텐츠 호환을 위해 누락 시 앱에서는 low로 표시한다.
- 새 Stage의 기본 난이도 배치는 Day 1~2 low, Day 3~5 medium, Day 6~7 high를 권장한다.
- low는 정보를 묻거나 간단히 도움을 요청하는 Day에 쓴다.
- medium은 지원 의사, 경험 설명, 일정 조율처럼 문장이 조금 길어지는 Day에 쓴다.
- high는 면접 답변, 조건 확인, 결과 회고처럼 상황 판단과 정중한 표현이 필요한 Day에 쓴다.


5. 이미지 경로 규칙
------------------

JSON에 들어가는 이미지 경로는 반드시 사이트 루트 경로로 쓴다.

  /content/conversations/stage-{stageId}/assets/stage-{stageId}-day-{DD}-cutscene.jpg
  /content/conversations/stage-{stageId}/assets/stage-{stageId}-day-{DD}-scene-01.jpg
  /content/conversations/stage-{stageId}/assets/stage-{stageId}-day-{DD}-scene-02.jpg
  /content/conversations/stage-{stageId}/assets/stage-{stageId}-day-{DD}-scene-03.jpg

역할 매핑
- cutsceneImagePath: Day 대표 이미지, 목록 카드 썸네일, 컷씬 단계
- sceneImages.intro: 나레이션 단계
- sceneImages.dialogue: 대화 단계
- sceneImages.review: 퀴즈와 핵심 표현 단계

상세 화면 fallback 순서
  sceneImages[role].imagePath
  -> cutsceneImagePath
  -> FALLBACK_CONVERSATION_CUTSCENE_PATH

주의
- sceneImages는 타입상 선택이지만, 새 Stage는 intro/dialogue/review를 모두 넣는 것을 표준으로 한다.
- 경로는 있는데 파일이 없으면 현재 UI에서 깨진 이미지가 보일 수 있다.


6. Narration
------------

ConversationNarration
  id     | string
  textKo | string
  textEn | string | 선택

원칙
- 장면 몰입용 문장으로 쓴다.
- 앱 기능 설명처럼 쓰지 않는다.


7. Dialogue Line
----------------

ConversationDialogueLine
  id             | string
  speakerId      | string | 선택. 예: learner, channa, staff
  speakerLabelKo | string | 선택. 예: 나, 챈나, 직원
  textKo         | string
  textEn         | string
  responseQuiz   | ConversationResponseQuiz | 선택

responseQuiz 원칙
- 사용자의 응답이 필요한 learner 대사에만 붙인다.
- Stage 1 표준은 Day당 2개다.
- responseQuiz의 정답 option text는 해당 dialogue line의 textEn과 일치해야 한다.
- 선택 후 실제 learner 대사가 화면에 이어지므로, JSON 설명문은 상황 안에서 자연스럽게 써야 한다.
- "이 대답이 내 대사로 이어집니다", "선택지를 고르세요"처럼 앱 구조를 설명하는 문장은 피한다.

ConversationResponseQuiz
  type            | "next-line-choice"
  promptKo        | string
  promptEn        | string | 선택
  options         | { id: string, text: string }[]
  correctOptionId | string
  explanationKo   | string | 선택
  explanationEn   | string | 선택

예시
{
  "id": "s1-d2-d4",
  "speakerId": "learner",
  "speakerLabelKo": "나",
  "textKo": "7시쯤이면 좋겠어요. 가능하면 창가 자리로 부탁드려도 될까요?",
  "textEn": "Around seven, please. Could we have a window seat if possible?",
  "responseQuiz": {
    "type": "next-line-choice",
    "promptKo": "직원이 원하는 시간을 물었습니다. 시간과 좌석 요청을 자연스럽게 말해 보세요.",
    "promptEn": "The staff asked what time you would like. Choose the best reply.",
    "options": [
      { "id": "a", "text": "Around seven, please. Could we have a window seat if possible?" },
      { "id": "b", "text": "Give me the boss table now." },
      { "id": "c", "text": "Windows are ugly." },
      { "id": "d", "text": "I'll sit in the kitchen." }
    ],
    "correctOptionId": "a",
    "explanationKo": "`Could we have ~, please?`는 좌석이나 추가 요청을 공손하게 말할 때 좋습니다."
  }
}


8. Key Expression
-----------------

ConversationKeyExpression
  id           | string | UserProgress.savedExpressions.expressionId와 매칭
  expressionEn | string
  expressionKo | string
  tipKo        | string | 선택

원칙
- Day 마지막에 중요한 표현을 단어장에 저장하는 흐름으로 사용한다.
- 저장은 keyExpressions[].id 기준으로만 한다.


9. Quiz
-------

ConversationQuiz는 데이터 타입을 유지한다.
multiple-choice, next-line-choice, pattern-fill-blank는 현재 회화 상세 화면에서 단어 풍선 문장 만들기(sentence-builder) UI로 렌더링한다.
blank-bubble-fill은 말풍선 안의 빈칸을 option bubble로 채우는 구현 완료 UI 패턴이며, 기존 sentence-builder를 대체하지 않고 추가 지원한다.
Phase 17 기준 Stage 1 Day 1의 s1-d1-q3-next-line 1문항에 시범 적용되어 있다.

공통 필드
  id              | string
  type            | "multiple-choice" | "next-line-choice" | "pattern-fill-blank" | "blank-bubble-fill"
  promptKo        | string
  promptEn        | string | 선택
  expressionId    | string | 선택
  explanationKo   | string | 선택
  explanationEn   | string | 선택
  options         | { id: string, text: string }[]
  correctOptionId | string

type별 의미
- multiple-choice
  - 데이터는 객관식 형태를 유지한다.
  - UI에서는 promptEn 또는 promptKo의 backtick 문장(`...`)이 있으면 그 문장을 단어 풍선 정답으로 사용한다.
  - backtick 문장이 없으면 correctOptionId의 option text를 정답 문장으로 사용한다.

- next-line-choice
  - 상대 대사를 먼저 보여주고, 이어질 답장을 만드는 문제다.
  - 추가 필드:
      partnerLineEn
      partnerLineKo
      partnerSpeakerLabelKo

- pattern-fill-blank
  - templateEn의 "{{blank}}"에 correct option text를 채운 문장을 정답 문장으로 사용한다.
  - 추가 필드:
      templateEn

- blank-bubble-fill
  - 말풍선 안에 templateEn 문장을 보여주고, "{{blank}}" 위치를 빈칸 bubble로 렌더링하는 타입이다.
  - correctOptionId가 가리키는 option text를 "{{blank}}"에 채우면 정답 문장이 된다.
  - 사용자는 option bubble 하나를 눌러 빈칸을 채우고, 정답 공개 전에는 채워진 빈칸을 다시 눌러 선택을 해제할 수 있다.
  - 기존 sentence-builder 문제를 제거하지 않고, 빈칸형 말풍선 UX가 필요한 quiz에만 사용한다.
  - templateEn은 반드시 "{{blank}}" 토큰을 포함해야 한다.
  - 추가 필드:
      templateEn
  - 예시:
      {
        "type": "blank-bubble-fill",
        "id": "s1-d1-q3-bubble",
        "expressionId": "s1-d1-k1",
        "templateEn": "Are you {{blank}} for dinner this Friday?",
        "promptKo": "초대 표현의 빈칸에 들어갈 자연스러운 단어를 고르세요.",
        "promptEn": "Complete the invitation bubble.",
        "options": [
          { "id": "a", "text": "free" },
          { "id": "b", "text": "late" },
          { "id": "c", "text": "closed" },
          { "id": "d", "text": "borrowed" }
        ],
        "correctOptionId": "a",
        "explanationKo": "`Are you free for ~?`는 약속이나 식사 초대에 자연스럽게 쓰는 표현이다."
      }

오답 기록
- 퀴즈 오답은 quiz[].id 기준으로 UserProgress에 기록한다.
- expressionId는 "이 퀴즈가 어떤 핵심 표현을 연습하는지"를 연결하는 보조 정보다.


10. 몰입형 문장 작성 원칙
------------------------

사용자에게 보이는 회화 문장은 장면 안에서 말해야 한다.

권장
- "직원이 원하는 시간을 물었습니다. 시간과 좌석 요청을 자연스럽게 말해 보세요."
- "친구가 주말에 영화를 볼 수도 있다고 했습니다. 자연스럽게 함께 가자고 제안하세요."
- "이 상황에서는 조금 어색해요. 더 자연스러운 말로 이어가 볼게요."

피하기
- "이 대답이 내 대사로 이어집니다."
- "정답 대사가 내 대사로 이어집니다."
- "내가 고른 답:"
- "앱에서 다음 단계로 이동합니다."
- "선택 후 learner 대사를 표시합니다."


11. Stage 추가 체크리스트
------------------------

새 Stage를 추가할 때 확인한다.

- stage-{stageId}/index.json이 있다.
- index.json의 dayFiles가 실제 파일명과 일치한다.
- 각 day-xx.json이 ConversationDay 객체 하나만 담는다.
- 각 Day에 difficulty를 넣는다. 값은 low, medium, high 중 하나다.
- 각 Day에 cutsceneImagePath가 있다.
- 각 Day에 sceneImages.intro/dialogue/review가 있다.
- 각 Day의 이미지 경로가 /content/conversations/stage-{stageId}/assets/... 형식이다.
- 각 Day의 narrations, dialogue, responseQuiz, keyExpressions, quiz 수량이 목표 표준과 맞다.
- responseQuiz는 learner 대사에 붙어 있고 정답 option text가 textEn과 일치한다.
- quiz는 sentence-builder 또는 blank-bubble-fill UI로 자연스럽게 풀 수 있는 문장 중심 데이터다.
- 사용자 저장/완료/오답 데이터에는 본문 문장을 저장하지 않고 참조 ID만 저장한다.
